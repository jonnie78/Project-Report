\section{Introduction} 

Particle detectors are complex pieces of equipment, typically comprising of various sub-detectors, each capable of detecting and measuring various attributes of particles such as energy, transverse momentum or track length. An example is the Compact Muon Solenoid (CMS) at CERN, which contains a tracker, electromagnetic calorimeter, hadronic calorimeter, and muon chamber \cite{CMS}. The large number of different entities involved in a particle detection experiment can make it challenging to simulate computationally, however the object orientated nature of C++ makes it an ideal candidate for this purpose.\\

This project sets out to create a C++ library that is able to simulate a particle detection experiment, complete with features such as detecting energy, particle identification, and missing energy calculations. The library consists of abstract base classes for particles and sub-detector components, with inheritance chains going down to the tangible particle and sub-detector objects. These particle objects consist of electron, muon, tau, neutrino, proton, pion, and photon, while the sub-detector objects are tracker, calorimeter, and muon chamber. A detector class is also present and used to contain sub-detector components and particle identification logic. The functionality of this library is demonstrated with multiple particle objects passed through a detector object based off the CMS experiment.

\section{Design and Implementation}

Both the particle and sub-detector classes follow an overarching inheritance chain model. The particle inheritance chain starts with an abstract base particle class that contains members which all particles own. The next tier down contains derived lepton, hadron, and photon classes, and the final tier contains specific leptons and hadrons. A similar model is followed for the sub-detector classes but with no intermediary tier. A stand alone detector class is also present and acts to hold sub-detector objects for particles to be passed through. These two structures are shown in Figures 1 and 2 respectively. \begin{figure}

\subsection{Particle Hierarchy}

At the top of the particle hierarchy is the abstract \texttt{Particle} base class, with it's data members and function shown in Figure 1. \texttt{four\_momentum} is defined as \texttt{unique\_ptr<FourMomentum>}, where \texttt{FourMomentum} is an object comprising of 4 doubles (E, px, py, pz) with getters and setters for all. The \texttt{FourMomentum} object also validates E such that its greater than 0, throwing an error message if it is, with px, py and pz able to be any value. An error is also thrown if E is less than \texttt{rest\_mass}, with this implemented in \texttt{Particle}'s parameterised constructor. A \texttt{unique\_ptr} was used as a particle's four momentum is deemed to be unique to itself and unable to be shared between particles. Due to following this structure, \texttt{Particle} obeys the rule of 5. While \texttt{paricle\_id} stores the ID a particle has, \texttt{id\_count} keeps count of the running total so that each particle has a unique ID, and is hence outside the main class body as static member. These 3 data members are all defined as private as derived classes have no reason to directly manipulate them. For \texttt{antiparticle\_status}, \texttt{true} corresponds to an anti-particle and \texttt{false} not, with this also directly altering charge via a ternary operator flipping charge for anti-particles. \texttt{print\_data()} is a pure virtual function that prints all data members contained within \texttt{Particle}. By defining it as a pure virtual function it ensures a generic particle object can't be created.\\

The next tier in the inheritance chain contains classes to reflect groupings of particles, namely hadrons and leptons, with an additional class for photons. \texttt{Photon} consists of \texttt{polarisation} as a private member as no classes inherit from \texttt{Photon}, with input validated via exception handling. \texttt{Lepton} and \texttt{Hadron} consist of \texttt{lepton\_number} and \texttt{baryon\_number} respectively, with both assigned via a ternary operator according to whether or not the particle is an anti-particle. \texttt{print\_data()} is also overridden for both reduce to code repetition in derived classes.\\

The final tier is made up of \texttt{Electron}, \texttt{Muon}, \texttt{Tau}, and \texttt{Neutrino} which inherit from \texttt{Lepton}, and \texttt{Proton} and \texttt{Pion} which inherit from \texttt{Hadron}. A neutron class was deliberately omitted as it would have had identical behavior to neutral pion and was hence deemed not meaningful to include. Each of these classes define a new data member specific to each particle, as well as override the \texttt{print\_data()} function to ensure all particle data and its name is printed. \texttt{Muon} and \texttt{Proton} define \texttt{track\_length} and \texttt{track\_curvature} respectively, which are both set to 0 on construction and then updated to a random value between 1 and 10 meters once the particle passes through a tracker object. \texttt{Electron} defines \texttt{is\_isolated} which is a boolean initially set to false, but updated randomly to true or false once it passes through a tracker object. \texttt{Neutrino} defines \texttt{flavour} which is set by the user and validated to Electron, Muon and Tau via exception handling. \texttt{Pion} and \texttt{Tau} both define \texttt{decay\_mode}, with the charge of a pion determining its decay mode; charged resulting in muonic decay and neutral two photon decay \cite{ParticleData}. For \texttt{Tau}, \texttt{decay\_mode} is randomly assigned as leptonic or hadronic, via a Mersenne Twister generator, according to the true probabilities of 35\% and 65\% respectively \cite{ParticleData}. All particles have their rest mass, charge, and for hadrons baryon number, assigned within the constructor except for pions where the user sets the charge. Charge is set by the user for pions due to the slightly different masses and decay modes charged and neutral pions possess. Due to this, validation of the charge must occur before its passed to the base class constructor which requires the usage of a static helper function to validate the charge.

\subsection{Detector Hierarchy}

At the top of the detector hierarchy sits the abstract \texttt{SubDetector} base class, with its data members and functions shown in Figure 2. Both \texttt{print\_data()} and \texttt{detect()} are pure virtual functions ensuring that a generic sub-detector object cannot be created. \texttt{detect()} takes \texttt{shared\_ptr<Particle> p} as its input due to the fact that particles are stored as \texttt{shared\_ptr<Particle>} to allow shared ownership as they pass through a sub-detector, if the particles are say stored in a vector.\\

\texttt{Tracker}, \texttt{Calorimeter}, and \texttt{MuonChamber} all inherit from \texttt{SubDetector}, overriding both inherited virtual functions and also defining new members as shown in Figure 2. All \texttt{int} type members defined by these classes are validated in their respective class constructors, while \texttt{material}, with the exception of \texttt{Calorimeter}, are validated via static helper functions before passing to the base class constructor, along with their type. As \texttt{Calorimeter} also possesses it's own \texttt{type}, this is taken as input from  the user instead of \texttt{material} and validated via a static helper function, which also sets \texttt{material} via a ternary operator before passing both to the base class constructor. The \texttt{detect()} function within \texttt{Calorimeter} acts to output the energy of particles passing through depending on it's type. Hadronic calorimeters output energy for hadrons and taus with a hadronic decay mode, and electromagnetic calorimeters for electrons and photons. As there is no clear way to group these particles their type is determined via the use of \texttt{dynamic\_pointer\_cast}, with this process for the hadronic calorimeter shown in the code snippet below. \texttt{dynamic\_pointer\_cast} is used specifically due to the fact that particles are stored as shared pointers. 
\begin{minted}[fontsize=\small]{cpp}
auto hadron = dynamic_pointer_cast<Hadron>(p);
auto tau = dynamic_pointer_cast<Tau>(p);
if ((type == "Hadronic") && (hadron || (tau && (tau->getDecayMode() == "Hadronic")))) {
    return p->getFourMomentum()->getE() * efficiency;
}
\end{minted}
Here \texttt{efficiency} acts as detector efficiency and is a random value between 0.8 and 1 generated by  a Mersenne Twister generator from the \texttt{<random>} library. \texttt{efficiency} is used within all sub-detectors \texttt{detect()} functions. \texttt{MuonChamber} follows a similar structure for its detection logic, using \texttt{dynamic\_pointer\_cast} to only output energy for muons and taus with leptonic decay mode. As well as this, if a particle is a muon, its \texttt{track\_length} member is updated to a value between 1 and 10 via \texttt{setTrackLength()}. The \texttt{detect()} function in \texttt{Tracker} outputs energy for all charged particles, so only requires the use of \texttt{dynamic\_pointer\_cast} to handle leptonic and hadronic taus before using an if statement to exclude neutral particles. \texttt{dynamic\_pointer\_cast} is used to type protons and electrons so that \texttt{track\_curvature} and \texttt{is\_isolated} can be updated to random values via their setters. The use of \texttt{dynamic\_pointer\_cast} was avoided where possible, such as in \texttt{Tracker}, to allow for easier modification of sub-detector detection logic if more particle classes were implemented.\\

The \texttt{Detector} class acts to store \texttt{SubDetector} objects and pass particles through their respective \texttt{detect()} functions, outputting the detected energies, missing energy, and particle identity, with its data members and functions shown in Figure 2. The \texttt{SubDetector} objects are stored in a vector as unique pointers to allow for run time polymorphism, which is required due to the \texttt{Dectector} object not knowing how many \texttt{SuDetector} objects it will contain when being constructed. As unique pointers are used \texttt{Detector} follows the rule of 5, however both the copy constructor and copy assignment are set to \texttt{delete} in the interface file as its deemed logical to only one \texttt{Detector} object at a time and hence there is no need to copy, which would adds unnecessary complication to the class if implemented. At construction, \texttt{name} is set to whatever the user input, and \texttt{total\_true\_energy} and \texttt{total\_detected\_energy} are set to 0. \texttt{SubDetector} objects are appended to \texttt{sub\_detectors} via \texttt{add\_sub\_detector()} which uses \texttt{move} due to the copy functions being set to \texttt{delete}. \texttt{print\_data()} prints the detector name as well as looping through \texttt{sub\_detectors} and calling all the \texttt{SubDetector} object's print functions. \texttt{detect()} first outputs the ID of the particle its detecting and its ture energy. Next, it defines a map and loops through all the sub-detectors in \texttt{sub\_detectors}, passing the particle through their detect functions and appending the sub detector type to the map key, and the outputted energy value to the corresponding value, also printing the energy each sub-detector outputs. In this loop, any energy detected by a \texttt{Calorimeter} object is accounted for, with \texttt{total\_detected\_energy} set to this outside the loop to keep a running total, as well as \texttt{total\_true\_energy} also summed, with this whole process shown in the code snippet below. 
\begin{minted}[fontsize=\footnotesize]{cpp}
map<string, double> results;
double calorimeter_energy = 0;
for (const unique_ptr<SubDetector>& sd : sub_detectors) {
    double energy = sd->detect(p);
    results[sd->getType()] = energy;
    cout<<" -"<<sd->getType()<<": "<<energy<<" MeV"<<endl;
    if(sd->getType() == "Electromagnetic Calorimeter" || sd->getType() == "Hadronic Calorimeter") {
        calorimeter_energy += energy;
    }
}
total_true_energy += p->getFourMomentum()->getE();
total_detected_energy += calorimeter_energy;
\end{minted}
Following this, the conditions for if a sub-detector has registered a hit are defined. They are defined as boolean whereby if the map contains a key matching the sub-detector \texttt{type}, and this key has a corresponding value greater than 0 the boolean is set to true. An example of this condition for a \texttt{Tracker} object is shown below.
\begin{minted}{cpp}
bool tracker_hit = results.count("Tracker") && results["Tracker"] > 0;
\end{minted}
