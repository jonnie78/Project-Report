\section{Introduction} 

Particle detectors are complex pieces of equipment, typically comprising of various sub-detectors, each capable of detecting and measuring various attributes of particles such as energy, transverse momentum or track length. An example is the Compact Muon Solenoid (CMS) at CERN, which contains a tracker, electromagnetic calorimeter, hadronic calorimeter, and muon chamber \cite{CMS}. The large number of different entities involved in a particle detection experiment can make it challenging to simulate computationally, however the object orientated nature of C++ makes it an ideal candidate for this purpose.\\

This project sets out to create a C++ library that is able to simulate a particle detection experiment, complete with features such as detecting energy, particle identification, and missing energy calculations. The library consists of abstract base classes for particles and sub-detector components, with inheritance chains going down to the tangible particle and sub-detector objects. These particle objects consist of electron, muon, tau, neutrino, proton, pion, and photon, while the sub-detector objects are tracker, calorimeter, and muon chamber. A detector class is also present and used to contain sub-detector components and particle identification logic. The functionality of this library is demonstrated with multiple particle objects passed through a detector object based off the CMS experiment.

\section{Design and Implementation}

Both the particle and sub-detector classes follow an overarching inheritance chain model. The particle inheritance chain starts with an abstract base particle class that contains members which all particles own. The next tier down contains derived lepton, hadron, and photon classes, and the final tier contains specific leptons and hadrons. A similar model is followed for the sub-detector classes but with no intermediary tier. A stand alone detector class is also present and acts to hold sub-detector objects for particles to be passed through. These two structures are shown in Figures 1 and 2 respectively. \begin{figure}

\subsection{Particle Hierarchy}

At the top of the particle hierarchy is the abstract \texttt{Particle} class, with it's data members and function shown in Figure 1. \texttt{four\_momentum} is defined as \texttt{unique\_ptr<FourMomentum>}, where \texttt{FourMomentum} is an object comprising of 4 doubles (E, px, py, pz) with getters and setters for all. The \texttt{FourMomentum} object also validates E such that its greater than 0, throwing an error message if it is, with px, py and pz able to be any value. An error is also thrown if E is less than \texttt{rest\_mass}, with this implemented in \texttt{Particle}'s parameterised constructor. A \texttt{unique\_ptr} was used as a particle's four momentum is deemed to be unique to itself and unable to be shared between particles. Due to following this structure, \texttt{Particle} obeys the rule of 5. While \texttt{paricle\_id} stores the ID a particle has, \texttt{id\_count} keeps count of the running total so that each particle has a unique ID, and is hence outside the main class body as static member. These 3 data members are all defined as private as derived classes have no reason to directly manipulate them. For \texttt{antiparticle\_status}, \texttt{true} corresponds to an anti-particle and \texttt{false} not, with this also directly altering charge via a ternary operator flipping charge for anti-particles. \texttt{print\_data()} is a pure virtual function that prints all data members contained within \texttt{Particle}. By defining it as a pure virtual function it ensures a generic particle object can't be created.\\

The next tier in the inheritance chain contains classes to reflect groupings of particles, namely hadrons and leptons, with an additional class for photons. \texttt{Photon} consists of \texttt{polarisation} as a private member as no classes inherit from \texttt{Photon}, with input validated via exception handling. \texttt{Lepton} and \texttt{Hadron} consist of \texttt{lepton\_number} and \texttt{baryon\_number} respectively, with both assigned via a ternary operator according to whether or not the particle is an anti-particle. \texttt{print\_data()} is also overridden for both reduce to code repetition in derived classes.\\

The final tier is made up of \texttt{Electron}, \texttt{Muon}, \texttt{Tau}, and \texttt{Neutrino} which inherit from \texttt{Lepton}, and \texttt{Proton} and \texttt{Pion} which inherit from \texttt{Hadron}. A neutron class was deliberately omitted as it would have had identical behavior to neutral pion and was hence deemed not meaningful to include. Each of these classes define a new data member specific to each particle, as well as override the \texttt{print\_data()} function to ensure all particle data and its name is printed. \texttt{Muon} and \texttt{Proton} define \texttt{track\_length} and \texttt{track\_curvature} respectively, which are both set to 0 on construction and then updated to a random value between 1 and 10 meters once the particle passes through a tracker object. \texttt{Electron} defines \texttt{is\_isolated} which is a boolean initially set to false, but updated randomly to true or false once it passes through a tracker object.

\subsection{Detector Hierarchy}

Pure abstract sub detector class (data members, setters getters, print functions) -> derived sub detector classes (detection of energy with traits of particles used where possible to determine which particles are detected, detector efficiency determined by random number generation, when particle traits not possible for determining if detected or not dynamic pointer cast used (muon and tau), this was also used when detectors set particle data memebers like track length and curvature, helper functions to validate material when needed) -> detector class (vector of shared ptrs to sub-detectors so rule of 5 used but no copy functions as logically theres one detector at a time and no need to copy, theyre defined but set to delete, this means move is used when adding sub-detectors in, function defined to add new sub-detectors so only name allocated when constructing object, determines particle type based off which detectors it sets off, prints detected energies, determines missing energy from calorimeters (from efficiencies and neutrinos), this means muons left out but this was the best way discuss later).
